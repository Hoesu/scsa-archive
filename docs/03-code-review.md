# 03. 코드 리뷰

코드 리뷰는 이 저장소에서 **가장 많이 배우는 시간**입니다.
같은 문제를 다른 사람은 어떻게 풀었는지 보고, 내 풀이와 비교하며 질문하는 것만으로도 실력이 늡니다.

## 리뷰할 PR 찾기

- [`풀이` 라벨이 붙은 열린 PR](https://github.com/Hoesu/scsa-archive/pulls?q=is%3Aopen+label%3A풀이)
- [나에게 리뷰 요청된 PR](https://github.com/Hoesu/scsa-archive/pulls/review-requested/@me)
- `리뷰-환영` 라벨이 붙은 PR
- **내가 이미 푼 문제**의 PR 을 리뷰하면 가장 깊이 있는 리뷰를 할 수 있어요.

## 리뷰 방법 (GitHub 화면)

1. PR 의 **Files changed** 탭으로 이동
2. 코멘트를 달고 싶은 줄 번호 옆의 **+** 를 클릭 (드래그하면 여러 줄 선택)
3. 코멘트 작성 후 **Start a review** (바로 올리지 않고 모아서 한 번에 제출)
4. 다 봤으면 우측 상단 **Review changes** → 종류 선택 후 **Submit review**

| 종류 | 언제 |
|---|---|
| **Comment** | 질문이나 의견만 남길 때 |
| **Approve** | 머지해도 좋다고 판단될 때 (사소한 제안이 남아 있어도 OK) |
| **Request changes** | 규칙 위반(파일 위치, 원문 복사 등)이나 명백한 오류가 있을 때만 |

### Suggested change (제안 코드)

코멘트 입력창의 **±** 아이콘(Add a suggestion)을 누르면 이렇게 작성할 수 있습니다.

````markdown
```suggestion
        if not answer or answer[-1] != n:
```
````

작성자는 **Commit suggestion** 버튼 한 번으로 반영할 수 있어요. 오타, 변수명 수정에 특히 유용합니다.

## 코멘트 말머리

의도를 분명히 하기 위해 코멘트 앞에 말머리를 붙여주세요.

| 말머리 | 의미 | 예시 |
|---|---|---|
| `[필수]` | 머지 전에 고쳐야 함 (규칙 위반, 버그) | `[필수] 이 파일은 solutions/ 안에 있어야 해요` |
| `[제안]` | 반영하면 더 좋지만 선택 | `[제안] deque 를 쓰면 pop(0) 대신 O(1) 로 꺼낼 수 있어요` |
| `[질문]` | 이해가 안 되거나 궁금함 | `[질문] 여기서 visited 를 큐에 넣을 때 체크하는 이유가 뭔가요?` |
| `[칭찬]` | 배울 점 | `[칭찬] 방향 배열을 쓰니까 훨씬 읽기 쉽네요!` |
| `[참고]` | 관련 자료, 다른 풀이 소개 | `[참고] 제 풀이는 이분 탐색으로 접근했어요 (링크)` |

## 무엇을 보면 좋을까? (체크리스트)

**정확성**
- [ ] 엣지 케이스(빈 입력, 최솟값/최댓값, 중복 값)를 처리하나요?
- [ ] 헤더에 복잡도를 적었다면, 실제 코드와 맞나요?

**효율**
- [ ] 입력 크기 대비 시간 복잡도가 충분한가요? (대략 1초 ≈ 1억 번 연산)
- [ ] 반복문 안에서 불필요하게 비싼 연산(리스트 `in`, 문자열 `+=`, `pop(0)`)을 하지 않나요?

**가독성**
- [ ] 변수/함수 이름만 보고 역할을 알 수 있나요?
- [ ] 매직 넘버 대신 의미 있는 상수를 썼나요?
- [ ] 헤더의 "접근" 설명만 읽고 코드를 따라갈 수 있나요?

**규칙**
- [ ] 파일 위치/이름이 맞나요? (자동 검사가 대부분 잡아줍니다)
- [ ] 문제 원문을 그대로 붙여넣지 않았나요?

## 좋은 리뷰 vs 아쉬운 리뷰

| 아쉬운 리뷰 | 좋은 리뷰 |
|---|---|
| "비효율적이네요" | "[제안] `list.pop(0)` 은 O(N) 이라 큐가 길어지면 느려져요. `collections.deque` 의 `popleft()` 를 쓰면 O(1) 이에요" |
| "이거 틀렸어요" | "[질문] 입력이 `[]` 일 때 7번 줄에서 IndexError 가 날 것 같은데, 확인해 보실 수 있을까요?" |
| "LGTM" 만 남기고 Approve | "[칭찬] 경계 조건 처리가 깔끔하네요. 저는 n=1 케이스를 놓쳤었는데 배웠습니다. Approve 합니다!" |

## 리뷰를 받는 사람에게

- 리뷰는 **코드에 대한 의견**이지 나에 대한 평가가 아닙니다.
- 모든 제안을 반영할 필요는 없어요. 반영하지 않을 때는 이유를 짧게 남겨 주세요.
- 리뷰해 준 사람에게 고맙다는 한마디는 큰 힘이 됩니다. 🙏
